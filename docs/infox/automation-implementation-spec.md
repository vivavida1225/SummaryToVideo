# InfoX 영상 생성과 기업 에셋 자동 대체 구현 명세

기준일: 2026년 11월 2일  
대상 프로젝트: `C:\WORKS\SummaryToVideo`  
대상 서비스: [InfoX 스튜디오](https://infox2.infomaxai.com/studio/home)

**2026-11-02 사용자 변경 요구 — 생성 결과의 원문 비교 제외:** 확정 snapshot과 실제 전송 대본은 그대로 유지한다. 시안 준비 검사에서는 InfoX가 반환한 `voiceover.content` 및 `segment_captions[].text`를 전송 원문과 비교하지 않는다. 영상 ID·기대 장면 수·장면별 비어 있지 않은 대본, 음성 파일·길이·음성/제공자/속도, 비어 있지 않은 자막과 유효한 순서/시간 구간은 계속 확인한다. 이 정책이 아래의 과거 “대본/자막 본문 일치” 요구를 대체한다. 에셋 저장 과정에서는 최신 서버 원본을 기준으로 대본·자막·음성·배치 보존 및 source/result 지문을 계속 검증한다.

**2026-11-02 사용자 변경 요구 — 확인 불가의 진행 허용:** 에셋의 unknown 판정은 미검출과 같은 진행 조건으로 처리하며 교체 대상에서 제외한다. unknown 판정·사유·개수와 읽지 못한 메타데이터 안내는 보존한다. 검출된 항목만 고정 즐겨찾기로 교체하며, 나머지 항목은 기존 보존 검증을 적용한다. 메타데이터 부족/해석 불가만으로 검사·계획·저장·편집기 이동을 보류하지 않는다. 메타데이터 텍스트 필드의 해석 깊이 초과도 metadata_unreadable로 안내하고 진행한다. 영상 식별·배정 구조·버전·ROOT/메타데이터 노드 탐색 한도와 전체 노드 예산·저장 지문/참조/타이밍 오류는 계속 각각의 계약에 따라 중단한다. 이 정책이 아래의 과거 “확인 불가 항목이 있으면 진행 보류” 요구를 대체한다.

사용자가 SummaryToVideo에서 수정한 최종 대본과 제작 설정으로 InfoX 시안을 생성하고, 자동 배치된 에셋 중 기업명이나 기업 관련 언급이 확인된 항목을 사용자 즐겨찾기의 관련 업종 영상으로 바꾼다. 교체 내용을 저장하고 서버에서 다시 확인한 다음, 사용자 브라우저를 해당 영상의 편집 화면으로 이동시킨다.

프로젝트 생성, 제작 시작, 즐겨찾기 검색, 에셋 교체 저장의 요청 구조는 사용자 실행 로그에서 확인했다. 완료 팝업의 종료 조건도 화면 소스에서 확인했다. 독립 HTTP 클라이언트의 인증, 실제 완료 이벤트 본문, 교체 후 서버 재조회와 최종 재생은 구현 과정에서 검증해야 한다. 현재까지 기능 코드는 구현하지 않았으며, 이 명세는 관찰한 계약과 구현 요구를 구분한다.

## 1 사용자 요구와 적용 범위

### 최종 동작

1. 사용자가 대본을 검토·수정하고 InfoX 제작을 요청한다.
2. 최신 편집본의 저장을 완료한 뒤 대본과 설정을 확정한다.
3. InfoX 프로젝트를 생성하고, 별도 요청으로 시안 제작을 시작한다.
4. 해당 영상과 작업의 완료 신호 및 편집 데이터 준비 상태를 확인한다.
5. 실제 자동 배정된 영상·사진에서 제한 기업의 명시적 언급을 찾는다.
6. 문제 항목을 사용자가 이미 등록한 즐겨찾기에서 업종 검색으로 찾은 영상 구간으로 대체한다.
7. 대본·음성·템플릿 배치·타이밍을 보존하며 저장하고, 서버 상태를 다시 읽어 적용 결과를 확인한다.
8. 사용자 브라우저에서 완료된 영상의 편집 화면을 연다.

현재 확정된 업종 검색어는 **반도체**다. 삼성·SK하이닉스 관련 에셋을 이 검색 결과로 대체한다. 다른 업종 검색어와 기업별 매핑은 설정으로 확장할 수 있지만, 관련 업종의 자동 추론이나 임의 검색어 선택까지 검증한 것은 아니다.

### 즐겨찾기 예외

**즐겨찾기에서 가져온 대체 에셋에는 기업명 제한을 다시 적용하지 않는다.** 사용자가 실제 영상을 시각적으로 확인하고 기업 노출 우려가 없다고 판단해 등록한 목록이기 때문이다.

따라서 제목·태그·설명 등에 삼성전자나 SK하이닉스가 있어도 허용한다. 즐겨찾기 검색 결과에 포함됐으면 제목에 검색어 ‘반도체’가 직접 들어 있는지도 별도로 요구하지 않는다. OCR·로고 검사나 추가 시각 검수를 즐겨찾기 후보의 사용 조건으로 붙이지 않는다. 파일 접근, 구간 참조, 길이, 미디어 형식 등 기술적 적용 가능성은 확인한다.

### 이번 기능에 포함하지 않는 작업

영업일 예약 실행, 검토 전 대본의 자동 전송, 최종 MP4 렌더링·다운로드·게시, 새 즐겨찾기 자동 등록은 포함하지 않는다. InfoX 시안 완료는 최종 영상 렌더링 완료와 별개다. 메타데이터 검사는 모든 프레임의 기업 로고 노출 부재를 보증하는 기능이 아니다.

## 3 전체 연동 구조

권장 구조는 **Vue 화면 → 로컬 FastAPI → InfoX HTTP API**다. 화면은 기존과 같이 로컬 API만 호출하고, 백엔드가 인증·제작 접수·이벤트 수신·에셋 검사·저장 상태를 관리한다. 현재 화면의 `connect-src 'self'` 정책과도 맞는다. 직접 HTTP 인증에 제약이 확인되면 브라우저 연동을 보완 수단으로 검토한다.

| 구성 요소 | 책임 |
| --- | --- |
| SummaryToVideo 화면 | 최신 편집본 저장, 제작 요청, 설정 표시, 진행·에셋 교체 결과 표시, 사용자 브라우저 이동 |
| InfoX 클라이언트 | 인증과 갱신, 요청·응답 검증, 읽기 재시도, 쓰기 요청의 불명확한 결과 구분 |
| 실행 관리자 | 로컬 실행 ID와 InfoX 영상·작업 ID 관리, 단계별 기록, 재시작 후 재개, 중복 요청 방지 |
| 에셋 검사기 | 실제 배정 참조 추출, 같은 파일의 메타데이터 연결, 기업명 검출과 즐겨찾기 출처 예외 |
| 즐겨찾기 검색기 | 업종 검색, 즐겨찾기 여부 확인, 구간 단위 후보 선택 |
| 교체 어댑터 | 레이어 종류·파일·구간 정보 갱신, 배치와 타이밍 보존, 변경 범위 검사 |
| 저장 검증기 | 최신 버전 사용, 저장 후 재조회, 실제 적용 결과와 보존 항목 비교 |

외부 제작 상태는 기존 대본 생성 작업의 `state`와 분리한다. 대본이 `completed`여도 InfoX 작업은 진행 중일 수 있고, InfoX 교체가 실패해도 원래 대본과 진단 기록은 남아 있어야 한다.

## 4 최신 대본 확정과 전송 설정

### 최신 편집본

`compressed.txt`는 최초 생성 결과다. 사용자가 수정한 최신 대본은 `edited_compressed.json`에서 복원되며 `JobManager.get()`의 `compressed`, `revision`에 반영된다.

구현 시 화면은 `flushCompressed()` 완료를 기다린다. 한글 조합 중이거나 저장에 실패하면 제작 요청을 보내지 않는다. 백엔드는 요청한 로컬 작업과 revision이 현재 값인지 확인하고 대본·revision·설정을 하나의 전송 스냅샷으로 저장한다. 전송 후 사용자가 다시 편집해도 이미 접수한 대본을 바꾸지 않는다.

전송 스냅샷에는 본문, revision, 본문 해시, 줄과 장면의 대응, 설정, 확정 시각을 기록한다. 관찰된 5줄·5장면은 실행 사례이며 숫자 5를 고정하지 않는다. 이번 요청은 비어 있지 않은 각 줄을 장면으로 사용했고 `voiceover`와 `context`가 동일했다. 빈 줄·줄바꿈 처리 규칙은 입력을 임의로 재작성하지 않는 범위에서 명시하고 검증한다.

기존 `needs_review` 진단은 전송 성공을 이유로 지우거나 정상 상태로 바꾸지 않는다. 이 상태에서 사용자의 직접 제작 요청을 허용할지에 대한 정책은 구현 전에 정해야 한다. 검토 필요 대본의 무검토 자동 전송은 이번 범위가 아니다.

## 5 InfoX API 계약

아래 상대 경로의 호스트는 `https://infox2.infomaxai.com`이다. 경로의 철자는 실제 요청의 `recommand`를 유지한다.

| 용도 | 메서드와 경로 | 핵심 계약 |
| --- | --- | --- |
| 로그인 | `POST /infomaxai/auth/login` | 응답에 `access_token`, `token_type=bearer`. 로그인 입력·추가 인증 조건은 별도 클라이언트에서 확인한다. |
| 토큰 갱신 | `GET /infomaxai/auth/refresh-token` | 경로는 확인했다. 갱신 자격·쿠키·실패 처리는 실검증한다. |
| 프로젝트 생성 | `POST /infomaxai/videos/create_video_new` | 본문 `video`, `context`. HTTP 200과 생성된 `id`를 확인했다. |
| 제작 시작 | `GET /infomaxai/worker/infox_generate_type_text/{video_id}` | HTTP 200, `message="generate_type_text"`, `taskid`. 작업을 시작하는 쓰기 동작이다. |
| 이벤트 구독 | `GET /api/stream?channel=infox:{video_id}` | SSE. 현재 영상 채널과 현재 작업 ID를 함께 추적한다. |
| 제작 이력 | `GET /infomaxai/videos/video_render_logs/{video_id}` | 시작 상태 응답을 확인했다. 완료 이력은 보조 확인 후보다. |
| 영상 상태 | `GET /infomaxai/videos/videostate/{video_id}` | 최상위 `id`, `video`, `script`, `can_edit`, `updated_at` 등을 확인했다. |
| 일반 영상 즐겨찾기 검색 | `POST /infomaxai/recommand/video` | 검색어와 `favorites_only=true`를 함께 전달한다. |
| 사용자 영상 즐겨찾기 검색 | `POST /infomaxai/recommand/uservideo` | 같은 필터 요청을 확인했으나 해당 실행의 결과는 0개였다. |
| 편집 데이터 저장 | `POST /infomaxai/context/update_video_context/{video_id}` | 본문 `video`, `contextData`, `updatedAt`. 응답 `status="Video updated"`, `updated_at`. |

프로젝트 생성 POST와 제작 시작 GET은 별도 단계다. 생성 응답의 `id`를 보관한 다음 제작 시작 경로에 사용하고, 그 응답의 `taskid`도 별도로 보관한다. 둘 중 한 단계만 성공했으면 전체 제작 접수 완료로 표시하지 않는다.

`videostate` 응답의 컨텍스트를 저장 본문의 `contextData`로 옮기는 정확한 매핑은 어댑터에서 검증한다. 생성 시의 `context`와 편집 저장의 `contextData`를 이름만 보고 동일한 키로 취급하거나 빈 객체로 대체하지 않는다. 버전은 조회 응답 `updated_at`에서 저장 요청 `updatedAt`으로 명시적으로 매핑한다.

## 6 인증과 연결 관리

InfoX 클라이언트 소스는 `auth_token`에서 읽은 값을 `Authorization: Bearer` 헤더에 넣고, 조직 장치 토큰이 있으면 `X-Org-Device-Token`도 설정한다. HAR에 인증 헤더가 생략됐다는 이유로 무인증 API로 취급하지 않는다.

구현 시 다음을 확인한다.

- 독립 HTTP 클라이언트의 로그인·토큰 갱신·필요 쿠키와 조직 장치 토큰 조건.
- 일반 API와 `/api/stream`의 인증 방식 및 인증 만료 후 재연결 방법.
- 401·403 등 인증 문제와 생성·에셋 처리 오류를 구분하는 응답 처리.
- 백엔드 재시작 후 자격 복원 또는 재로그인 안내와 기존 실행 재개.
- 기본 사용자 브라우저의 InfoX 로그인 상태와 해당 영상 접근 권한.

백엔드 로그인은 사용자 브라우저 로그인을 자동으로 만들지 않는다. 토큰을 URL에 붙여 편집 화면을 열지 않는다. 자격은 백엔드 전용 비밀 저장 수단으로 관리하고, 대본·실행 상태·Git 문서·일반 로그에 복사하지 않는다. 비밀번호·토큰·쿠키·장치 토큰·서명 URL을 오류 메시지에도 그대로 기록하지 않는다.

현재 로컬 API의 `X-App-Token`, Host·Origin 검사와 경로 검증은 유지한다. 이 로컬 앱 토큰과 InfoX 토큰은 서로 다른 용도다.

## 7 시안 완료 판정

### 화면 코드에서 확인한 계약

현재 `taskid`의 메시지를 고르고, 그 메시지의 완료 상태로 팝업을 닫는다.

```javascript
messages.find(message => message.additional_kwargs.taskid === taskid)
message.additional_kwargs.task_status === "completed"
```

진행 바는 별도 필드인 `additional_kwargs.progress`를 퍼센트와 CSS 너비로 표시한다. 팝업이 닫히면 `taskpopup` 쿼리를 제거한다. 영상 데이터가 포함된 SSE 메시지 처리에서는 영상 상태를 반영하고 `videostate`를 다시 조회해 대본 편집 보기를 선택한다.

이는 화면 소스에서 확인한 계약이다. 로그의 SSE 이벤트 본문은 비어 있어 실제 수신 JSON의 전체 외피, 오류 상태명, 재연결·재전송 계약은 실연결로 확정해야 한다. 알 수 없는 상태명을 임의로 성공으로 해석하지 않는다.

### 완료 처리 순서

1. 현재 `video_id`의 채널을 구독하고 현재 `taskid`에 해당하는 이벤트만 처리한다.
2. 해당 작업의 `task_status="completed"`를 완료 신호로 사용한다. `additional_kwargs.error` 등 명시적 오류 정보가 있으면 성공으로 진행하지 않는다. 오류 상태의 구체 형식은 실제 수신 계약으로 확정한다.
3. 최신 `videostate`를 읽고 현재 전송 스냅샷에 해당하는 결과인지 확인한다.
4. 이번 직접 입력 방식에서는 장면별 `voiceover.content`가 전송 대본과 같고, 음성 파일과 `segment_captions` 등 편집 데이터가 준비됐는지 확인한다.
5. 이벤트와 저장 반영 사이에 지연이 있으면 제한된 횟수·시간 안에서 읽기를 재시도한다.
6. 편집 데이터가 준비되면 에셋 검사·교체 단계로 이동한다.

다른 템플릿이나 제작 방식에서 음성이 없거나 자막 구조가 달라질 경우에는 별도 준비 상태 검증기를 사용한다. 이번 관찰값을 모든 템플릿의 필수 계약으로 확대하지 않는다.

### 단독 완료 조건으로 사용하면 안 되는 값

| 값 | 이유 |
| --- | --- |
| `progress=100` | 화면 표시값이다. 완료 상태·편집 데이터 준비와의 실제 이벤트 순서는 미확인이다. |
| `videosgenerationend` | 화면의 ‘비디오 생성 완료’ 상태명은 확인했으나 실제 완료 이력 응답은 없다. |
| `can_edit=true` | 생성 전후 모두 true였다. 권한과 준비 완료를 구분해야 한다. |
| HTTP 200 | 요청 처리 성공이며 제작 결과 준비를 보장하지 않는다. |
| 일정 시간 경과 | 약 44초는 한 실행의 관찰 시간일 뿐이다. |
| `render_preview` 또는 MP4 존재 | 시안 완료 후에도 `render_preview`는 없었다. 최종 렌더링을 요구하지 않는다. |
| 기존 `captions` 필드 | 완료된 장면도 null이었고 실제 자막은 `segment_captions`에 있었다. |

SSE 연결이 끊기면 같은 영상·작업의 상태를 재확인한다. 재연결 때 이미 끝난 작업의 완료 신호를 놓칠 수 있으므로 초기 상태 조회와 이벤트 구독 사이의 경합도 처리해야 한다. `video_render_logs`를 대체 완료 신호로 쓸 때는 실제 완료 응답과 작업 대응을 먼저 확인한다. 확인하지 못한 경우에는 상태를 ‘확인 중’으로 남기고 새 제작 요청을 보내지 않는다.

## 8 실제 배정 에셋 추출과 기업명 검사

### 검사 대상 참조

```text
video.scenes[i].rootShape.layers[layer_id].props.media
video.scenes[i].rootShape.layers[layer_id].props.media.image_files[j]
```

레이어 사전의 모든 항목을 무조건 검사하지 않는다. 장면의 `ROOT`에서 `child`를 따라 연결된 실제 배치 레이어를 확인한다. 이번 자동 배정 범위는 `props.aigeneratable.auto_select === true`인 레이어에서 찾았다. 이 표식이 다른 템플릿에도 그대로 적용되는지는 확인하고, 구조를 알 수 없는 템플릿을 검사 완료로 처리하지 않는다.

사진 묶음은 부모 `media`가 아니라 `image_files[]`의 각 파일이 실제 배정 대상이다. 배열에 항목이 있으면 그 항목들을 검사하고 부모의 남아 있는 템플릿 제목을 실제 사진 제목으로 취급하지 않는다. 직접 영상 레이어는 부모 미디어의 파일·구간 참조를 사용한다. 이후 새로 생성된 에셋과 사용자가 직접 수정한 배치를 혼동하지 않도록 참조 식별자를 보관한다.

### 메타데이터 연결

배정 객체에 제목이나 설명이 없으면 같은 장면의 `rerank_result`, 필요 시 `search_metadata`에서 동일한 파일을 찾는다. 사진은 **`bucket + filename`의 정확한 일치**로 연결한 사례를 확인했다. 영상은 원영상 ID만으로 연결하지 않고 선택 구간의 `segment`·파일 참조까지 확인한다.

서명 URL의 쿼리를 식별자로 쓰거나 제목 유사도로 파일을 추정하지 않는다. 연결한 메타데이터의 출처 경로를 검사 결과에 남긴다. 부모 제목 ‘너굴 뉴스 그래픽’처럼 과거 템플릿 값이 남아 있을 수 있다.

| 검사 필드 예 | 의미 |
| --- | --- |
| `title`, `title_ko`, `video_title_raw` | 에셋 제목과 원제 |
| `tags` | 기업명·업종 등 태그 |
| `description`, `text_body` | 설명·기사 본문 등 연결 정보 |
| `img_description_ai`, `frame_visual_caption` | 이미지·영상 장면 설명 |
| `frame_stt` | 해당 구간의 발화 텍스트 |

필드는 에셋 종류별로 존재 여부가 다르다. 대본·검색어·미사용 검색 후보를 통째로 검사해 배정 에셋으로 오인하지 않는다. 미사용 검색 메타데이터에 기업명이 남는 것과 실제 배치에 기업 에셋이 남는 것은 별개다.

### 기업명과 별칭

현재 사용자 요구에 포함된 표현은 `삼성전자`, `SK하이닉스`, `삼성`, `SK`, `하이닉스`, `삼전닉스`다. `삼전닉스`는 최초 조사 때 검토 후보였지만 이후 사용자가 명시해 현재 제한 목록에 포함한다. `삼전`, `하닉`, 기타 영문 별칭은 자동으로 추가하지 않고 설정 목록으로 관리한다.

검사본에 한해 유니코드·대소문자·공백을 정규화하고 원본 메타데이터는 보존한다. `SK`는 ASCII 영숫자 단어 내부를 피한다. 예를 들어 다음 규칙은 `sketch` 등의 오탐을 줄이는 출발점이다.

```regex
(?<![A-Za-z0-9])SK(?![A-Za-z0-9])
```

실제 표기 변형, 한글과 붙은 표현, 구두점은 예제로 검증한다. 검사 결과에는 장면·레이어·묶음 항목, 파일 식별자, 검출 필드·표현, 연결 메타데이터 출처를 기록한다.

### 판정 결과

| 판정 | 처리 |
| --- | --- |
| 기업명 검출 | 즐겨찾기 업종 영상으로 대체할 대상에 포함한다. |
| 메타데이터 검사 후 미검출 | 검사한 정보에서 미검출임을 기록한다. 시각적 노출 부재로 표현하지 않는다. |
| 메타데이터 부족·연결 실패 | 확인 불가로 표시한다. 안전 판정이나 근거 없는 자동 교체로 바꾸지 않는다. |
| 해당 배치의 검증된 즐겨찾기 대체 이력 있음 | 기업명 제한을 면제한다. 파일·구간·배치가 그 이력과 일치해야 한다. |

단순히 미디어에 `is_favorite=true`가 있다는 이유만으로 모든 자동 배정 항목을 면제하지 않는다. 이번 예외는 **사용자 즐겨찾기 검색에서 가져와 대체한 출처**에 적용한다.

## 9 즐겨찾기 업종 검색과 후보 선택

### 확인된 검색 요청

```http
POST /infomaxai/recommand/video
Content-Type: application/json
```

```json
{
  "skip": 0,
  "limit": 50,
  "search": "반도체",
  "include_politics": false,
  "sort_by": "relevance",
  "search_mode": "relevance",
  "date_from": "2025-11-02",
  "favorites_only": true
}
```

`date_from`은 캡처 당시 조건이다. 운영 날짜와 무관하게 이 값을 영구 고정하지 않고, 의도한 검색 기간을 설정으로 정한다. 즐겨찾기 검색의 결과가 잘리는 원인이 되지 않도록 날짜 필터의 실제 의미도 확인한다.

응답은 `total`, `items`, `skip`, `limit`를 포함한다. `items`는 원영상 전체가 아닌 **영상 구간**이다. 캡처에서는 결과 12개, 원영상 7개였고 모두 `is_favorite=true`였다. 이 중 제목에 SK하이닉스가 있는 2개도 허용한다. 이 숫자와 결과 순서를 운영 상수로 사용하지 않는다.

`/infomaxai/recommand/uservideo`에도 같은 검색·즐겨찾기 조건이 전달됐지만 결과는 0개였다. 초기 구현에서 이를 지원한다면 결과가 있는 경우의 스키마와 교체 호환성을 검증해야 한다. 일반 영상 결과와 같다고 추정해 무조건 합치지 않는다.

### 후보 선택 요구

- 검색어와 `favorites_only=true`를 함께 사용하고, 선택 후보가 해당 응답의 즐겨찾기 항목임을 확인한다.
- 전체 결과가 필요하면 `total`과 페이지 크기에 따라 `skip`을 진행한다. 첫 50개가 전부라고 가정하지 않는다.
- 후보의 `videoId`와 `segment`를 함께 보관한다. 같은 원영상의 서로 다른 구간을 중복으로 합치지 않는다.
- 기업명 문구, 제목에 업종어가 없는 이유, 추가 시각 검수 요구로 후보를 탈락시키지 않는다.
- 기술적으로 사용할 수 있는 후보 중 하나를 선택하고 그 선택을 실행 이력에 고정한다. 재시도할 때 임의로 다른 구간을 뽑지 않는다.
- 여러 대상을 교체할 때의 순환·중복 사용 정책은 설정으로 명시한다. 현재 요구는 검색 결과 중 하나를 사용하는 것이며 무작위 선택은 필수가 아니다.
- 결과가 없거나 사용 가능한 구간이 없으면 이유를 표시한다. 일반 검색 결과나 새 즐겨찾기 등록으로 자동 우회하지 않는다.

업종 일반화 설계안은 `replacement_search_by_company` 같은 매핑에 현재 기업 목록과 `반도체`를 연결하는 방식이다. 매핑이 없는 기업을 새로 탐지했을 때 업종을 임의 추론하지 않는다.

## 10 에셋 교체와 구간 정보 정리

### 로그에서 확인한 교체

`replace3`의 2장면에는 다음 두 사진이 배정돼 있었다.

- ‘삼성전자·SK하이닉스 반도체 공장 후보지’: 제목·태그·본문·AI 설명에서 관련 기업명 검출.
- ‘호남권 반도체 공장 후보지로 거론되는 3곳’: 제목에는 기업명이 없지만 연결한 태그·본문에서 삼성전자·SK하이닉스 검출.

첫 사진이 삭제된 후 남은 문제 사진이 즐겨찾기 영상으로 바뀌었다. 대상은 `ImageLayer`에서 `VideoLayer`가 됐고 `image_files`는 빈 배열로 정리됐다. 이후 즐겨찾기 구간 추가·삭제 과정에서는 `MediaLayer`와 다시 단일 `VideoLayer`로 저장되는 형태도 확인했다. UI의 클릭 순서를 모두 재현할 필요는 없지만 최종 저장 구조의 유효성은 지켜야 한다.

### 보존할 값과 바꿀 값

| 구분 | 요구 |
| --- | --- |
| 보존 | 장면 ID·순서, 루트 연결, 레이어 ID·배치 순서·위치·크기·효과, 전체 및 장면 타이밍, 대본·음성·자막, 다른 에셋, `contextData`와 기타 무관한 필드 |
| 교체 | 해당 배치의 파일·bucket·구간·원영상 ID, 선택 구간의 제목·해상도·길이·썸네일 등 미디어 속성, 필요한 레이어 종류와 묶음 구조 |
| 구조 검사 | 실제 사용하는 참조에 기존 문제 파일이 남지 않아야 하며, 새 미디어에 맞는 레이어 타입이어야 한다. |
| 비교 검사 | 적용 전후 전체 데이터를 비교해 허용한 대상 미디어·종류 이외의 변경을 탐지한다. |

사진 묶음 전체가 문제인 경우를 단일 영상으로 바꾼 기록은 있다. **정상 사진과 문제 사진이 섞인 묶음의 일부만 영상으로 대체하는 경우**, 여러 레이어, 서로 다른 장면·템플릿의 변환은 별도 검증이 필요하다. 정상 항목까지 버리고 묶음 전체를 한 영상으로 덮어쓰는 일반 규칙으로 확대하지 않는다.

### 정확한 구간 참조

선택한 후보의 `segment`는 구간 파일이다. 원영상 ID만 넣거나 원영상의 첫 부분으로 바꾸면 사용자가 확인한 구간과 달라질 수 있다. 관찰된 단일 영상 저장에서는 `media.filename`과 `media.segment`가 선택 후보의 `segment`에 대응했다.

`replace2`의 선택 구간은 원영상 `frameIndex=9`, `timestamp≈54.054초`, 길이 `6.01초`였다. 저장된 `startFrameVideo=0`, `endFrameVideo=180`, 프로젝트 `30fps`, `muted=true`는 **구간 파일 안의 재생 범위**다. 원영상의 timestamp를 구간 파일의 시작 프레임으로 다시 적용하지 않는다. 180을 모든 영상의 종료 프레임으로 고정하지도 않는다.

### 마지막 로그의 불일치와 구현 요구

| `replace3` 저장본 | 관찰 내용 |
| --- | --- |
| HAR 98 | `filename`과 `segment`가 모두 검색 결과 0번의 구간이었다. 부모 제목에는 예전 템플릿 값이 남았다. |
| HAR 106 | `filename`은 결과 0번, `segment`는 결과 2번으로 서로 달랐다. |
| HAR 118 최종 | `filename`, `segment`, `videoId`, 썸네일은 결과 3번에 대응하지만, `id`, `frameIndex`, `timestamp`, `preview_presigned`, `segment_url_presigned`는 결과 2번 값이 남았다. |

인덱스는 0부터 시작한다. 최종 파일 참조에 대응하는 결과 3번은 ‘중국 대만 반도체’, `frameIndex=5`, `timestamp≈30.030초`다. 저장된 부가 구간 정보는 `frameIndex=6`, `timestamp≈36.036초`였다. 두 결과 모두 승인된 즐겨찾기이지만 정확한 구간 식별은 일관되지 않다. 실제 편집기·렌더러가 어떤 필드를 우선하는지는 아직 검증하지 않았다.

교체 어댑터는 기존 부모 미디어에 후보 일부만 덧씌우지 말고, 선택한 **동일 후보의 파일·segment·videoId·구간 ID·frameIndex·timestamp·썸네일·미리보기 참조**를 일관되게 구성한다. 기존 배치 속성과 후보 미디어 속성을 명시적으로 구분하고, 새 후보에 없는 이전 에셋의 값은 호환 계약에 맞춰 제거하거나 갱신한다. 서명 URL은 영구 식별자가 아니므로 만료 후 갱신 방식도 확인한다.

### 길이와 음성

`replace3`의 전체 길이는 약 `65.4667초`, 대상 장면은 `12.87초`, 대체 영상은 `6.01초`였다. 저장본에서 장면 길이는 유지됐지만 부족한 구간을 반복·정지·늘리기 중 어떤 방식으로 재생하는지는 확인되지 않았다.

초기 구현은 장면·대본 타이밍을 바꾸지 않는 것을 기준으로 한다. 장면보다 짧거나 긴 영상의 처리 방식, 프레임 반올림, 크롭과 비율 변환, 빈 구간 여부를 실제 편집기와 재생으로 검증한다. 관찰된 `muted=true`를 기본으로 소재 원음을 꺼 TTS를 보존하고, TTS 길이·자막·음성 파일을 교체 과정에서 재생성하지 않는다.

## 11 저장과 서버 재조회

```http
POST /infomaxai/context/update_video_context/{video_id}
Content-Type: application/json
```

본문의 외형은 다음과 같다. 아래 코드는 자리표시자를 포함한 구조 설명이다.

```text
{
  "video": <대상 미디어만 교체한 최신 video 전체>,
  "contextData": <보존한 최신 편집 컨텍스트>,
  "updatedAt": <최신 조회 또는 직전 저장 응답의 updated_at>
}
```

성공 응답은 HTTP 200, `status="Video updated"`, 새 `updated_at`이었다. `replace3`의 후속 5건은 모두 직전 응답의 `updated_at`을 다음 요청의 `updatedAt`으로 보냈다. 이는 버전 연결 근거이며, 실제 충돌 응답의 HTTP 코드·형식은 별도로 확인해야 한다.

구현 순서는 다음과 같다.

1. 최신 상태와 버전을 읽고 검사 기준 스냅샷을 저장한다.
2. 문제 파일과 대상 레이어가 여전히 그 상태인지 확인한다.
3. 교체 계획을 적용하고 무관한 필드가 바뀌지 않았는지 비교한다.
4. 최신 버전을 포함해 저장한다. 여러 저장이 필요하면 응답 버전을 차례로 연결한다.
5. 성공 응답과 버전을 보관하고 `videostate`를 다시 조회한다.
6. 새 파일·구간·레이어 구조, 실제 문제 파일 제거, 대본·음성·타이밍·무관한 배치 보존을 확인한다.
7. 검증된 서버 버전과 배치에 교체 출처 이력을 연결한 뒤 편집 가능 상태로 표시한다.

부모 미디어에서 지운 파일이 `image_files`에 남아 있거나, 그 반대인 경우도 검사한다. 미사용 검색 후보·대본의 기업명까지 삭제하지 않는다. 전체 JSON의 직렬화 순서나 서버의 갱신 시각 차이 대신 의미 있는 참조·보존 항목을 비교한다.

사용자가 InfoX에서 동시에 편집했으면 오래된 전체 JSON을 강제로 덮어쓰지 않는다. 최신 데이터를 다시 읽고 대상이 같은 경우에만 교체 계획을 재평가한다. 저장 응답을 받지 못했다면 먼저 서버를 읽어 이미 적용됐는지 확인한다. 마지막 사용자 로그에는 이 독립 재조회가 없으므로 실제 연동 검증의 필수 항목이다.

교체 대상이 없으면 교체 쓰기 요청을 생략한다. 확인 불가 항목이 있거나 필요한 교체가 미완료면 ‘모든 교체 완료’로 표시하지 않는다. 편집기에서 사용자가 해결할 수 있도록 수동 열기 경로는 제공한다.

### 실행 기록

| 기록 | 필요한 값 |
| --- | --- |
| 대본 스냅샷 | 로컬 job ID, revision, 본문·해시, 장면 대응, 설정, 확정 시각 |
| 외부 작업 | InfoX 영상 ID·taskid, 현재 단계, 생성·접수 시각, 마지막 확인 상태, 편집 URL |
| 진행 확인 | 실제 수신 상태, 마지막 이벤트·조회 시각, 재연결·오류 정보 |
| 검사 결과 | 장면·레이어·항목, 원래 파일·구간, 검출 필드·용어·메타데이터 출처, 확인 불가 항목 |
| 교체 계획 | 업종 검색어·필터·시각, 후보 출처, 선택 후보의 videoId·segment·구간 정보, 대상 배치 |
| 저장 검증 | 저장 전후 버전, 응답, 재조회 결과, 무관한 필드 보존 결과 |
| 화면 이동 | 편집 준비 시각, 해당 사용자 화면에서 열기 처리한 실행 ID |

즐겨찾기 출처는 대상 배치와 선택 파일·구간에 묶어 저장한다. 같은 레이어가 나중에 다른 파일로 바뀌면 과거 예외를 그대로 적용하지 않는다. 동일한 검증된 대체 배치의 재검사는 기업명 제한을 면제해 무한 교체를 막는다. `is_favorite`나 제목만으로 이력을 복원하지 않는다.

로컬 파일 저장을 사용한다면 임시 파일과 원자적 교체를 사용하고, 실행 ID·경로·파일명을 검증한다. 상태 기록에는 식별에 필요한 안정된 파일 키를 보관하되 인증값·서명 URL 값은 넣지 않는다. 재개에 필요한 전체 서버 스냅샷은 비공개 진단 자료로 분리하고 민감 값을 정리한다.

## 13 사용자 화면과 편집기 이동

제작 버튼 근처에는 템플릿, TTS·속도, 직접 대본 입력, 업종 검색어, 자동 대체 사용 여부를 확인할 수 있게 한다. 전송된 대본 revision과 현재 편집본이 달라졌으면 그 차이를 알 수 있게 표시한다. 진행 UI는 ‘시안 제작’, ‘기업 에셋 확인’, ‘즐겨찾기 교체’, ‘저장 확인’처럼 사용자가 이해할 단계로 보여 준다.

에셋 결과에는 예를 들어 ‘2장면 사진 — 태그에서 SK하이닉스 검출 → 즐겨찾기 반도체 영상으로 대체’처럼 표시한다. 후보 없음·메타데이터 부족·저장 충돌은 해당 배치와 원인을 함께 보여 준다. 즐겨찾기 후보에 기업명이 있다는 추가 경고나 재승인 절차를 만들지 않는다.

### 편집 주소

```text
기본 편집 화면
https://infox2.infomaxai.com/studio/library/videos/{video_id}

대본 보기로 여는 관찰된 주소
https://infox2.infomaxai.com/studio/library/videos/{video_id}?chatboxView=script

제작 진행 팝업을 포함하는 주소
https://infox2.infomaxai.com/studio/library/videos/{video_id}?taskpopup={taskid}
```

InfoX 자체는 제작 시작 직후 마지막 주소로 이동한다. 이번 요구는 SummaryToVideo가 완료와 필요한 에셋 교체를 확인한 뒤 편집 화면을 여는 것이다. 완료 후 열 때 `taskpopup`을 붙이지 않는다. `chatboxView=script`는 관찰된 대본 보기 옵션이며 타임라인 초기 보기의 필수 조건으로 고정하지 않는다.

브라우저 이동은 실제 사용자의 화면에서 수행한다. 백엔드가 URL을 반환했다고 이미 열렸다고 기록하지 않는다. 비동기 완료 후 새 탭 열기는 팝업 차단에 걸릴 수 있으므로, 제작 버튼 클릭 때 로컬 대기 탭을 확보한 뒤 완료 시 이동시키는 방식을 검토한다. 기존 앱 탭에서 이동하는 방식도 선택할 수 있다. 사용자가 탭을 닫았거나 로그인이 만료됐으면 편집 URL과 다시 열기 버튼을 제공하고 중복 탭 열기를 피한다.

기존 InfoX 탭을 지정해 이동시키려면 해당 탭을 제어할 수 있는 별도 연결이 필요하다. 일반 웹 화면에서 임의의 기존 탭에 바로 push할 수 있다고 가정하지 않는다. URL은 허용된 InfoX 호스트와 현재 실행의 영상 ID로 구성하고 인증값을 포함하지 않는다.

## 15 구현 순서와 완료 기준

### 단계별 구현 개요

기존 Vue·FastAPI 구조를 유지하고 다음 7단계로 구현한다. 각 단계의 완료 기준을 통과한 뒤 다음 기능을 연결한다. 실행 기록과 중복 방지 구조는 초기에 마련하고, 마지막 단계에서 전체 흐름의 복구를 검증한다.

| 단계 | 구현 내용 | 완료 기준 |
| --- | --- | --- |
| 1 InfoX 연결 검증 | 백엔드 로그인·토큰 갱신, 기존 영상 조회, 즐겨찾기 검색, SSE 연결 | 독립 HTTP 클라이언트에서 인증·조회가 되고 이벤트 본문을 수신한다. |

| 5 즐겨찾기 선택과 교체 구성 | 반도체 즐겨찾기 검색, 구간 선택, 로컬 JSON 교체 계획·변환 | 기업명 예외를 지키고 모든 구간 참조가 동일 후보를 가리키며 무관한 데이터는 보존된다. |
| 6 저장과 적용 검증 | 최신 버전으로 저장, 서버 재조회, 편집기 재생 확인 | 문제 파일이 제거되고 정상 배치·대본·음성·타이밍이 유지된다. |

### 1단계 InfoX 연결 검증

`backend/infox/client.py`에 해당하는 HTTP 어댑터부터 구현한다. 인증·갱신과 일반 API, SSE의 인증 요구를 구분하고 필요한 자격을 백엔드 비밀 저장에 연결한다. 기존 영상의 `videostate`와 즐겨찾기 반도체 검색을 읽어 응답 구조를 확인한다.

SSE는 기존 영상 채널에 실제 연결해 메시지 외피와 본문 수신 방식을 확인한다. 완료 이벤트를 관찰하려면 제작이 필요하므로, 현재 작업의 실제 `completed` 값과 실패 처리는 3단계의 단일 생성 실행에서 검증한다. 이벤트 본문이 누락된 HAR만으로 수신 계약을 확정하지 않는다.

- **산출물:** 인증·갱신·조회·검색·SSE를 담당하는 어댑터와 민감 값을 제거한 응답 예시.
- **완료 기준:** 독립 클라이언트로 조회와 갱신이 가능하고 SSE 본문을 읽을 수 있다. 인증 만료를 다른 처리 오류와 구분한다.

### 2단계 실행 기록과 대본 확정

`App.vue`의 `flushCompressed()` 완료 후 백엔드가 `JobManager.get()`의 최신 대본과 revision을 확인해 설정과 함께 스냅샷으로 확정한다. 전송 이후의 추가 편집은 기존 실행과 분리한다.

`store.py`, `service.py`에 해당하는 실행 저장·관리 계층을 마련한다. 실행 ID, 단계, 대본 버전, 요청 의도와 접수 여부, 이후 확보할 `video_id`·`taskid`를 원자적으로 저장한다. 버튼 중복 클릭과 응답 유실을 구분하고, 불명확한 접수 상태에서 쓰기 요청을 다시 보내지 않는 구조를 이 단계부터 사용한다.

- **산출물:** 전송 스냅샷, 실행 기록 저장소, 중복 실행 방지, 실행 조회 API.
- **완료 기준:** 최초 `compressed.txt` 대신 최신 편집본이 선택된다. 저장 실패·한글 조합 중·revision 충돌 시 전송하지 않는다. 기록을 다시 읽어 실행 상태를 복원할 수 있다.

### 3단계 생성과 완료 추적

생성 POST 응답의 영상 ID를 기록하고, 그 ID로 제작 시작 GET을 호출해 작업 ID를 기록한다. 화면에는 기본 제작 버튼과 단계별 진행 상태를 연결한다. 두 단계 접수와 완료 대기는 백엔드 실행 관리자가 수행한다.

현재 영상 채널과 현재 작업의 실제 완료 이벤트를 확인하고, 이후 `videostate`에서 전송한 대본·장면·음성·자막 준비 상태를 검증한다. 중복 이벤트, 연결 중단, 이벤트보다 데이터 저장이 늦는 경우도 처리한다. 이 단계에서는 에셋 교체 없이 생성 결과까지 연결하며 편집 URL을 수동으로 열어 확인할 수 있게 한다.

- **산출물:** 앱에서 시작해 시안 준비 상태까지 추적하는 첫 번째 사용 가능 기능.
- **완료 기준:** 단일 실행의 영상·작업 ID가 끝까지 연결되고, 실제 완료 신호 및 결과 일치를 확인한다. `progress=100`, `can_edit=true`, 일정 시간 경과만으로 완료 처리하지 않는다.

### 4단계 기업 에셋 검사

`assets.py`에 해당하는 검사 모듈에서 ROOT에 연결된 실제 자동 배정 참조를 추출한다. 사진 묶음의 개별 파일과 직접 영상 참조를 구분하고, 파일 식별자로 같은 장면의 메타데이터를 연결한다.

현재 기업명·별칭 목록과 SK 경계 규칙을 적용해 장면·레이어·항목·검출 필드·표현을 반환한다. 메타데이터 부족은 확인 불가로 남긴다. 기존에 검증된 즐겨찾기 교체 이력이 있다면 같은 배치·파일·구간인지 확인해 예외를 적용한다. 이 단계에서는 검사 결과를 화면에 표시하며 외부 배치를 수정하지 않는다.

- **산출물:** 네트워크 쓰기 없이 검증 가능한 검사기와 사용자용 문제 에셋 목록.
- **완료 기준:** 제목 없는 사진의 태그·설명에서도 기업명을 검출한다. 대본·미사용 후보·템플릿의 오래된 제목·`sketch`를 오탐하지 않는다.

### 5단계 즐겨찾기 선택과 교체 구성

`favorites_only=true`, `search="반도체"`로 검색한 결과에서 사용할 구간을 선택하고 출처를 기록한다. 기업명 문구나 업종어의 제목 포함 여부로 재검열하지 않는다. 결과 없음·파일 사용 불가·페이지 초과는 별도로 처리한다.

교체 어댑터는 서버에 보내기 전에 로컬 JSON에서 변환을 수행한다. 파일·segment·원영상 ID·구간 ID·frameIndex·timestamp·썸네일·미리보기 참조를 같은 후보로 맞추고, 필요한 레이어 종류와 묶음 구조를 구성한다. 전체 데이터 비교로 허용한 대상 이외의 변경을 검사한다. 이 단계는 교체 계획과 변환 검증까지이며 서버 저장은 6단계에서 연결한다.

- **산출물:** 선택 후보와 즐겨찾기 출처 이력, 교체 계획, 적용 전후 변경 비교.
- **완료 기준:** 마지막 로그에서 발견한 혼합 구간 정보가 재현되지 않는다. 사진·영상 변환과 정상·문제 항목이 섞인 묶음에서 무관한 배치를 보존한다. 재시도 시 선택 구간이 임의로 바뀌지 않는다.

### 6단계 저장과 적용 검증

최신 상태와 버전에서 교체 대상이 여전히 같은지 확인하고, 검증한 변환을 적용해 저장한다. 응답의 `updated_at`을 후속 요청에 연결하고 저장 성공 뒤에는 반드시 서버 상태를 다시 읽는다. 충돌과 응답 유실을 처리할 때는 적용 여부부터 조회한다.

사진에서 영상으로의 전환, 다중 배치와 혼합 묶음, 장면보다 짧고 긴 구간을 실제 편집기에서 확인한다. 원래 TTS·자막·배치·장면 길이는 보존하며, 부족한 영상 길이의 반복·정지 등 재생 계약을 확인한다. 기존 로그는 저장 성공까지만 입증하므로 재조회와 실제 재생이 이 단계의 핵심 검증이다.

- **산출물:** 저장·재조회로 확인된 자동 대체 기능과 배치별 검증 결과.
- **완료 기준:** 실제 사용 참조에서 문제 파일이 없어지고 선택한 즐겨찾기 구간이 적용된다. 대본·음성·정상 에셋·레이어 위치와 크기·타이밍은 유지되며 새로고침 후에도 적용과 재생을 확인한다.

### 7단계 브라우저 이동과 복구 완성

필요한 교체의 저장·재조회가 끝난 `ready_for_editor` 상태에서 사용자 브라우저를 해당 편집 URL로 이동시킨다. 제작 버튼 클릭 때 확보한 대기 탭 또는 선택한 이동 방식을 사용하고, 팝업 차단·닫힌 탭·로그인 만료에는 다시 열기 경로를 제공한다.

인증 만료, SSE 연결 중단, 쓰기 응답 유실, 저장 충돌, 화면·백엔드 재시작을 전체 흐름에서 검증한다. 복구는 보관한 영상·작업·구간 선택과 서버 상태를 기준으로 수행하며, 이미 접수한 제작이나 적용한 교체를 다시 실행하지 않는다. 후보 없음·확인 불가·교체 미완료는 원인을 표시하고 수동 편집 경로를 제공한다.

- **산출물:** 생성 요청부터 자동 대체와 사용자 편집기 이동까지 연결된 기능.
- **완료 기준:** 올바른 영상이 한 번 열리고, 중단 후 재개해도 프로젝트·제작·에셋 교체가 중복되지 않는다. 백엔드가 URL을 반환한 것과 사용자 브라우저가 실제로 열린 것을 구분한다.

### 단계별 도입 범위

- **1~3단계:** 생성 자동화와 시안 완료 확인을 먼저 사용할 수 있다.
- **4~6단계:** 기업 에셋 검사와 즐겨찾기 자동 대체를 추가한다.
- **7단계:** 브라우저 이동과 전체 흐름의 복구를 완성한다.

초기 적용은 현재 템플릿·TTS 설정과 반도체 즐겨찾기 검색으로 한정하고, 해당 흐름을 끝까지 검증한 뒤 다른 템플릿·업종으로 확장한다. 단계별 검증은 해당 기능의 회귀 검증으로 남기며, 단계 완료를 이유로 아직 구현하지 않은 후속 동작까지 완료로 표시하지 않는다.

특히 3단계의 실제 완료 이벤트, 5단계의 일관된 구간 참조, 6단계의 혼합 묶음·길이 처리·서버 재조회는 다음 단계 진행 전에 해결해야 하는 조건이다.

### 검증 항목

| 영역 | 통과 기준 |
| --- | --- |
| 편집 저장 | 조합 중 입력·저장 실패·revision 충돌에서 잘못된 대본을 전송하지 않는다. 최초 생성본 대신 최신 편집본을 보낸다. |
| 요청 구성 | 본문과 장면 대응이 일치하고 설정의 값·자료형을 보존한다. 템플릿 기본 음성으로 선택 음성을 덮어쓰지 않는다. |
| 접수 | 생성 ID로 제작 시작을 호출하고 taskid를 기록한다. 중복 클릭·타임아웃에 중복 제작을 보내지 않는다. |
| 완료 | 실제 이벤트에서 현재 영상·작업을 구분하고 완료·실패를 처리한다. 100%나 can_edit만으로 성공하지 않는다. |
| 준비 상태 | 전송 대본·장면·음성·자막 데이터를 확인한다. 이벤트 중복·재연결·상태 반영 지연을 처리한다. |
| 검사 범위 | 실제 연결된 자동 배정 파일만 검사한다. 미사용 검색 후보와 대본은 제외한다. |
| 메타데이터 | 제목 없는 사진도 동일 파일의 태그·설명에서 검출한다. 템플릿 부모 제목·정보 부족을 올바르게 처리한다. |
| 기업 표현 | 삼성전자·SK하이닉스·삼성·SK·하이닉스·삼전닉스를 검출하고 sketch 등은 SK로 오탐하지 않는다. |
| 즐겨찾기 예외 | 기업명이 있는 즐겨찾기도 허용한다. 제목에 업종어가 없어도 검색 결과면 허용한다. 반복 검사에서 재교체하지 않는다. |
| 검색 실패 | 0건·페이지 초과·사용 불가 파일을 구분하고 비즐겨찾기로 자동 우회하지 않는다. |
| 구간 일관성 | 같은 원영상의 다른 구간을 구분한다. 파일·segment·ID·frameIndex·timestamp·미리보기 참조가 같은 후보에 대응한다. |
| 사진·영상 변환 | 단일·다중 배치, 사진에서 영상, 기존 영상 교체를 검증한다. 정상 에셋과 섞인 묶음에서 무관한 항목을 보존한다. |
| 타이밍·재생 | 짧고 긴 구간, 반복·정지 처리, 프레임 범위, 크롭, 음소거, TTS·자막 보존을 실제 편집기에서 확인한다. |
| 저장 | 최신 버전 사용, 충돌 감지, 응답 유실 후 조회, 서버 재조회로 적용·보존 결과를 확인한다. |
| 재개 | 앱·백엔드 재시작 후 같은 실행을 복원하고 생성·제작·대체를 중복하지 않는다. |
| 브라우저 | 사용자의 로그인 브라우저에서 올바른 영상이 열리고 팝업 차단·닫힌 탭·로그인 만료를 처리한다. |
| 민감 정보 | 토큰·계정정보·원본 HAR·서명 URL이 Git·일반 실행 로그·URL·오류 메시지에 노출되지 않는다. |

오프라인 검증에는 식별자와 민감 값을 제거한 요청·응답 fixture를 사용한다. 원본 대형 HAR 전체를 테스트나 Git에 넣지 않는다. 실제 접수 검증은 중복 생성이 발생하지 않도록 단일 실행의 영상·작업 ID를 끝까지 연결해 수행한다.

기능 완료는 **최신 대본과 설정으로 생성 → 해당 작업의 시안 완료 확인 → 문제 배정 에셋을 승인된 즐겨찾기 업종 구간으로 대체 → 일관된 참조로 저장·서버 재조회 → 사용자 브라우저 편집 화면에서 적용과 재생 확인**까지 통과했을 때로 정의한다. 후보가 없거나 확인 불가 항목이 있으면 그 상태와 원인을 정확히 보여 주는 것도 완료 기준에 포함한다.
