# InfoX 시황 영상 자동화 요구사항과 분석 근거

2026년 10월 30일 대화와 사용자가 제공한 InfoX 네트워크 기록을 정리한다. 목표는 SummaryToVideo에서 **사용자가 직접 수정한 최종 대본을 전송하고, 설정을 적용해 시안 제작을 시작한 다음, 완료되면 사용자 브라우저를 해당 편집 화면으로 이동**시키는 것이다.

프로젝트 생성과 제작 시작의 HTTP 요청, 실제 설정값, 편집 화면 주소는 확인했다. FastAPI 백엔드에서 직접 연동하는 방식을 우선 검토할 수 있다. 다만 독립 클라이언트 인증과 시안 완료 판정은 실검증 전이며, 이 문서를 추가하는 시점에 연동 기능은 구현하지 않았다.

## 문서와 예제

- [요청 본문 예제](create-video-request.example.json): 관찰된 필드와 설정값을 유지하고 제목·설명·대본을 표시용 문자열로 대체했다.
- [분석 근거](har-analysis-2026-10-30.json): 요청 인덱스, 파일 무결성 정보, 관찰된 결과와 검증 범위를 기록했다.

원본 HAR, 로그인 비밀번호, 토큰 값, 쿠키, 계정정보, 생성된 영상·작업 ID 값은 포함하지 않는다. 템플릿 ID와 음성 ID는 요청을 구성할 때 사용하는 설정값이다. 제공한 기록에는 원본 인증값이 포함돼 있으므로 원본 HAR는 저장소에 추가하지 않는다.

## 대화에서 정리된 사용자 요구

사용자는 매 영업일 SummaryToVideo에서 AI 시황 영상의 대본을 만든다. 현재는 대본을 직접 검토·수정한 뒤 InfoX에 붙여넣고, TTS와 제작 방식 등을 설정해 생성 버튼을 누른다.

이번 자동화의 사용자 흐름은 다음과 같다.

1. SummaryToVideo에서 대본을 직접 수정하고 최종 내용을 저장한다.
2. 사용자가 InfoX 제작을 요청하면 그 시점의 최종 대본과 설정을 전송한다.
3. 프로젝트를 생성하고 시안 제작 작업을 시작한다.
4. 시안 제작의 완료 또는 실패를 확인한다.
5. 성공하면 사용자 브라우저에서 해당 영상의 편집 화면을 자동으로 연다.

사용자는 InfoX 진행률이 100%가 되면 편집 화면으로 넘어가는 것으로 관찰했다. **목표는 완료 후 편집 가능한 화면으로 연결하는 것**이며, 생성 접수만 성공한 상태를 완료로 표시하면 안 된다.

매 영업일 사용한다는 배경은 예약 실행 요구와 구분한다. 이번 논의에는 영업일 스케줄러, 대본의 무검토 자동 전송, 최종 영상 렌더링, MP4 다운로드, 외부 게시까지의 자동화는 포함하지 않았다.

## 확인된 요청 순서

대상 사이트는 [InfoX 스튜디오](https://infox2.infomaxai.com/studio/home)이며, 아래 경로는 같은 호스트를 기준으로 한다.

| 순서 | 메서드와 경로 | 입력 및 응답 | HAR 항목 |
| --- | --- | --- | --- |
| 프로젝트 생성 | `POST /infomaxai/videos/create_video_new` | `video`, `context` JSON을 보내고 `id`를 받는다. HTTP 200이며 응답의 `context`가 요청과 완전히 같다. | 197 |
| 제작 시작 | `GET /infomaxai/worker/infox_generate_type_text/{video_id}` | 앞에서 받은 `id`를 사용한다. HTTP 200, `message=generate_type_text`, `taskid`가 반환된다. | 198 |
| 진행 기록 조회 | `GET /infomaxai/videos/video_render_logs/{video_id}` | 관찰된 상태는 `videosgenerationstart`이다. | 235 |
| 영상 상태 조회 | `GET /infomaxai/videos/videostate/{video_id}` | 생성 직후 영상 데이터를 반환한다. | 237 |
| 이벤트 연결 | `GET /api/stream` | `text/event-stream`이지만 기록된 응답 본문은 0자다. | 236 |

HAR 항목 번호는 `log.entries` 배열의 **0부터 시작하는 인덱스**다. 프로젝트 생성 시각은 한국 시간 2026년 10월 30일 15시 38분 38초였다.

제작 시작 경로는 GET이지만 작업을 시작하는 부작용이 있다. 프로젝트 생성 POST만 구현하면 제작 접수까지 재현한 것이 아니다. 두 요청의 성공 상태와 반환 ID를 각각 보관해야 한다.

## 최신 편집본을 전송하는 방법

전송된 `inputText`는 해당 로컬 작업의 `edited_compressed.json`에 저장된 **revision 10의 텍스트와 정확히 일치**했다. 최초 생성 결과인 `compressed.txt`와는 달랐다. 요청의 5개 장면은 입력 5줄을 그대로 사용했고, 각 장면의 `voiceover`와 `context`도 같았다.

현재 프로젝트는 최초 생성본과 사용자 편집본을 구분해 보관한다. 따라서 자동화가 `compressed.txt`만 직접 읽으면 사용자가 수정하기 전 대본을 보낼 수 있다. 다음 연결 방식을 사용해야 한다.

- 프런트엔드에서는 `flushCompressed()`가 완료돼 최신 편집본이 저장된 뒤 전송을 시작한다.
- 백엔드에서는 `JobManager.get()`으로 읽은 최신 `compressed`와 `revision`을 요청 시점에 확정한다.
- 전송한 대본 버전과 설정을 기록해, 사용자가 전송 후 다시 편집하더라도 이미 접수된 내용과 구분한다.

원래 대본에 `needs_review`가 남아 있을 때의 전송 허용 조건은 구현 시 정할 항목이다. 직접 편집한 대본을 보내려는 사용자 의도를 보존하되, 기존 진단 기록을 자동으로 정상 상태로 바꾸지 않는다.

## 편집 화면 주소와 완료 판정

실제 요청의 Referer와 InfoX 생성 화면 코드에서 다음 주소 패턴을 확인했다.

```text
편집 화면: /studio/library/videos/{video_id}
작업 팝업 포함: /studio/library/videos/{video_id}?taskpopup={taskid}
```

생성 화면 JavaScript의 처리 순서는 프로젝트 생성, 제작 시작 응답에서 `taskid` 취득, 위 `taskpopup` 주소로 `router.push`이다. 즉 **InfoX의 라우팅 코드는 제작 완료 전부터 해당 영상 페이지로 이동**한다. 사용자에게 보이는 100% 이후 변화는 이 주소 안에서 표시되는 진행 UI와 편집 화면 전환일 수 있으며, 이 부분의 실제 동작은 별도 검증이 필요하다.

화면 코드에는 다음 상태 표시가 있다. 이는 **클라이언트 소스에서 확인한 상태명과 표시 문구**이며, 이번 영상에서 실제 완료 응답을 관찰했다는 의미는 아니다.

| 상태 | 화면 코드의 표시 |
| --- | --- |
| `videosgenerationstart` | 비디오 생성 시작 |
| `videosgenerationend` | 비디오 생성 완료 |
| `videosgenerationerror` | 비디오 생성 실패 |

사용자 요구대로 우리 앱에서 완료까지 기다렸다가 편집 화면을 열려면, 해당 작업의 완료 상태와 영상의 편집 가능 시점이 일치하는지 확인해야 한다. `videosgenerationend`는 우선 확인할 후보이며, 완료 조건으로 확정하지 않는다. 실제 작업 ID와 영상 ID가 일치하는 이벤트·상태만 추적해야 한다.

대안으로는 제작 시작 직후 `taskpopup` 주소를 열어 InfoX의 기존 진행 화면을 사용하는 방법이 있다. 이는 사용자 요구의 ‘우리 앱에서 완료 후 이동’과 표시 시점이 다르므로, 같은 동작이라고 간주하지 않는다.

생성 직후 조회에는 템플릿 초기 장면 3개, `script=null`, `render_preview` 없음이 기록됐다. 이 값은 최종 결과가 아니며, 입력 5장면이 3장면으로 줄었다는 증거도 아니다. 시안 제작 완료와 최종 MP4 렌더링 완료를 구분해 검증한다.

## 인증과 사용자 브라우저

로그인 경로는 `POST /infomaxai/auth/login`, 토큰 갱신 경로는 `GET /infomaxai/auth/refresh-token`이다. 로그인 응답에는 `access_token`과 `token_type=bearer`가 있다. HAR에 포함된 클라이언트 코드는 `auth_token`에서 읽은 토큰을 `Authorization: Bearer` 헤더에 설정하며, 조직 장치 토큰이 있으면 `X-Org-Device-Token`도 설정한다.

HAR에서 민감 헤더가 보이지 않는다고 무인증 API로 해석하면 안 된다. 다음 항목은 실제 연동 과정에서 검증해야 한다.

- 별도 HTTP 클라이언트의 인증과 갱신, 만료·서버 재시작 후 재연결.
- 현재 조직에서 장치 토큰이 필요한 조건.
- 사용자 브라우저에서 InfoX 로그인 세션이 유지되는지와 편집 URL 접근 권한.
- 백엔드에서 로그인했다고 사용자 브라우저도 로그인되는 것으로 가정하지 않는 처리.
- 시안 완료 시 기본 브라우저 또는 지정한 탭으로 이동하는 동작과 로그인 만료 시 안내.

## 구현 시 보존할 상태와 실패 처리

권장 구성은 SummaryToVideo 화면이 로컬 API를 호출하고 FastAPI 백엔드가 InfoX와 통신하는 방식이다. 현재 화면 정책도 `connect-src 'self'`이므로 이 구조와 맞는다. 브라우저 자동 조작은 HTTP 인증 등에 추가 제약이 확인될 때 검토할 대안이다.

구현 시에는 다음 상태와 동작을 보존한다.

- 사용자가 전송한 대본의 버전, 설정, 로컬 작업 ID, InfoX 영상 ID, 작업 ID와 접수 단계를 저장한다.
- 프로젝트 생성은 성공했지만 제작 시작이 실패하면 기존 영상 ID를 보존한다.
- 타임아웃으로 접수 여부가 불명확하면 조회로 확인하고, 바로 새 프로젝트를 만들거나 제작을 다시 시작하지 않는다.
- 제작 시작 GET에 일반 조회 GET의 자동 재시도 정책을 그대로 적용하지 않는다. 서버의 중복 방지 키 지원 여부는 확인되지 않았다.
- 실패·중단 상태는 성공으로 표시하지 않으며, 재시도 대상과 이미 접수된 요청을 구분한다.
- 완료 판정 이후에는 해당 영상의 편집 화면으로 이동하며, 시안 완료를 최종 렌더링 완료로 표시하지 않는다.

## 검증 범위와 다음 확인 사항

원본은 56,103,504바이트이며 끝부분이 JavaScript 응답 문자열 중간에서 끊겼다. 전체 JSON은 파싱되지 않았지만, 그 앞의 완전한 HAR 항목 267개를 추출했다. 0부터 센 항목 267은 미완성이며 이후 기록의 존재·내용은 판단하지 않는다. 핵심 요청 두 개와 응답, 편집 주소 근거, 완료 상태명을 표시하는 클라이언트 소스는 완전한 항목 안에 있다.

원본 SHA-256은 `dea0d0385ff84529ce26a021fe7478615bfbcd960ad6488177347b4f52baf762`다. 근거 JSON에 필요한 항목 번호와 리소스 경로를 남겼으며 원본은 변경하지 않았다.

| 항목 | 확인 상태 |
